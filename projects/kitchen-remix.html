Knowing where the model is guessing

Kitchen Remix turns a photo of a real kitchen into previews of new cabinets, counters, floors and paint, running FLUX.1 Kontext locally so family photos stay on the machine. Every edit is sorted by how much the model has to invent, and the ones that invent get labelled.

Built for my parents' remodel 3 honesty tiers Fixed seed across A/B sets Local, RTX 4090
01The problem

A confident render of a wall that is not there

Most people remodeling a kitchen cannot picture the result. Showroom samples do not show your kitchen with that finish, and designer renders cost money and time.

AI image tools will cheerfully generate anything you ask for, including changes they have no basis for. That is worse than no render, because it invites a real spending decision based on a guess. So the design question was never what the model can do. It was what the model can do reliably, and how to keep everything else visibly marked.

02The answer

Three tiers, sorted by how much gets invented

TierEditsWhy it can or cannot be trusted
Core Finish swaps, A/B comparison, layered edits, object removal None of these need information the photo does not already contain. Changing a surface, or filling in a wall the model can already see. Treated as dependable previews.
Experimental Moving an object, opening or removing a wall The model invents geometry it cannot know: the scale of a moved object, the room beyond a wall. Labelled in-app as not dimensionally accurate. Directional feel, never measurement.
Stretch Structural change with supplied geometry (depth map, edge image, rough blockout) The honest way to do structural work. The layout comes from the user and the model only adds realism on top. Scoped and stubbed, not yet wired in.

Showing where that line sits, and refusing to let the model cross it quietly, is the whole product.

03Output

What it actually produces

Every pair below is one photograph in and one render out, on a stock kitchen the model had never seen. Left is the input, right is the result.

Finish swap

Core tier. The instruction names one surface and asks for everything else to hold still.

Appliance replacement

The refrigerator is swapped for a different one. The cabinetry it sits in does not move.

Fixture replacement

Same idea, different object class. The fixtures change; their number and hanging position do not.

One seed, three finishes

This is the reason a fixed seed matters. Three separate generations, one changed word each, and the room stays the same room. Without it you are comparing three different kitchens and learning nothing.

04Build notes

The decisions that made comparison fair

  • One seed across an A/B set. Only the instruction changes between variants, so the composition holds still and you are comparing finishes rather than comparing two different kitchens.
  • The model loads once and stays in VRAM. Reloading per request is slow and risks running out of memory. Inference runs in a worker thread so the API never blocks.
  • Presets as data, not code. Two JSON files hold the curated edit instructions, which is why a new finish is a one-line change.
  • The server boots without the ML stack. It reports model_loaded: false and stays testable on a machine with no GPU, which is how the interface got built and reviewed away from the 4090.
  • An export that a contractor can hold. A one-page spec sheet from the chosen previews, because the output of this product is a conversation with a human who does the actual work.
