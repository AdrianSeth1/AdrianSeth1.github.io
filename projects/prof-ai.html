A lecture assistant that never phones home

prof-ai listens to a live lecture, answers questions out loud from the professor's own materials, and flags the concepts the lecture skipped. Every part of it runs on one machine in the room. A Baylor professor uses it in class.

Deployed · live classroom use $0 per query No student audio leaves the room 5 screens, one local machine
01The problem

The obvious version of this product is unadoptable

Students fall behind in lectures for boring, fixable reasons. A term goes undefined. A step gets skipped. A question feels too small to interrupt for.

An AI assistant could catch all of that. Pointing a cloud assistant at a live classroom means streaming students' voices and a professor's unpublished slides to somebody else's servers, which is a non-starter for most instructors and reasonably so. Add a per-query bill and a procurement process and the project dies before it starts.

Running everything locally removes all three objections at once. There is no bill, no vendor, and no data leaving the room, which is why a professor could just start using it. That constraint drove every technical decision underneath.

02In class

What it does while the lecture is running

The live screen transcribes on-device with faster-whisper, keeps a running segment and word count, and lets the professor hand the room over to the assistant mid-sentence. Answers are retrieved from the uploaded course materials and spoken back through Piper.

The panel on the right is the part I care about most. Every answer carries the document and location it was drawn from, so a student can go read the source instead of trusting the machine. If retrieval finds nothing in the course materials, the answer says so rather than reaching for the open internet.

03The feature that justifies the build

Gap analysis

Transcription and Q&A are table stakes. Gap analysis is the reason a professor keeps it open.

After class, the system compares the full transcript against the documents linked to that session and reports where the lecture asserted something the reading treats as load-bearing. Each finding quotes the moment in the transcript, timestamps it, and cites the source it should have matched. Concepts that were covered well get marked covered, because a report that only ever complains gets ignored.

Look at the first finding. The lecture said NMDA receptors "need depolarization" and never explained the magnesium block that causes it. Students walked out with the rule and no mechanism. That is a two-minute fix at the start of the next class, and it is invisible without something reading the transcript against the reading.

04The rest of the surface

Grounded chat, materials, modules

Outside class hours the same corpus backs a research chat with a visible reasoning trace and source chips on every answer.

05Build notes

What was actually hard

  • The state machine, not the models. Lecture, awaiting, processing and speaking are distinct states with different microphone behaviour. Getting the hand-off right so the assistant does not talk over the professor took more iteration than the retrieval pipeline did.
  • Silence detection in a noisy room. The gate that decides a question has finished adapts to ambient noise with a slow moving average, because a fixed threshold that works in an empty room fails in a full one.
  • Designing next to the user. I scoped this sitting beside the professor and changed it based on what actually happened in class, which is how the gap-detection feature appeared at all. It was not in the original plan.
  • Everything resident. Whisper, the embedding store, the language model and the voice all stay loaded. Cold-starting any of them mid-lecture is the difference between a tool and a distraction.
